## 二、逐题拆解

### 问题 1：开始菜单搜不到 Git Bash

**现象**：Win 键搜 `git bash` 只出网页结果；但 `git --version` 能输出 `2.55.0.windows.3`。

**原因**
- 机器上只有某软件自带的**便携版 git**（`D:\...\vendor\PortableGit\mingw64\bin\git.exe`），解压即用，不写注册表、不注册开始菜单快捷方式。
- 便携版 ≠ 安装版：安装版会一并配置快捷方式、右键菜单、系统 PATH。

**解决**：https://git-scm.com/download/win 安装 Git for Windows（一路 Next），装完开始菜单出现 "Git Bash"。

**知识点**
- `where git`（Windows）/ `which git`（Linux）：按 PATH 顺序找可执行文件。
- PATH 是"命令名 → 可执行文件路径"的查找列表；有 exe 但不在 PATH 里，就只能写全路径调用。
- 便携版适合临时环境，长期开发必须装安装版。

**口述 30 秒**
> 命令能不能直接用，取决于两件事：在不在 PATH、有没有安装入口。`where git` 能定位到 exe 但开始菜单搜不到，说明是绿色版工具。这个判断方法对所有命令行工具通用。

### 问题 2：`ssh-keygen` 第一次静默失败

**现象**：执行后既无报错也无文件；`cat ~/.ssh/id_ed25519.pub` 提示 `No such file or directory`。

**原因**：`~/.ssh` 目录还不存在。`ssh-keygen` 在部分环境下不会自动创建父目录，写文件失败时退出码不显眼。

**解决**
```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
ls -la ~/.ssh/          # 必须验证产物
cat ~/.ssh/id_ed25519.pub
```

**知识点**
- **ed25519 vs RSA**：ed25519 密钥更短（68 字符 vs RSA 长串）、更安全、握手更快，现代默认选它。
- 公钥（`.pub`）给别人、私钥（无后缀）自己留着，**私钥永不外传**。
- 私钥权限必须是 600，否则 ssh 拒绝使用（"UNPROTECTED PRIVATE KEY FILE"）。
- Linux 工具常"安静失败"，习惯是**每步验证产物**：`ls` 看文件、`ps` 看进程、`ss` 看端口。

**口述 30 秒**
> Linux 下很多工具失败时不吵不闹，所以每次操作后要主动验证结果。生成了文件没有、进程还在不在、端口听没听——这三个检查能挡住大部分"看起来执行了其实没执行"的问题。

### 问题 3：`Host key verification failed`

**现象**：`ssh -T git@github.com` 直接报这条，**没有出现 yes/no 询问**。

**原因**
- SSH 首次连接陌生主机时，会把对方的**主机公钥指纹**存进 `~/.ssh/known_hosts`，以后每次比对，防止中间人劫持（MITM）。
- 首次连接必须人工回答 yes 才能写入。**非交互终端无法回答 → 直接判定失败**。

**解决**
```bash
# 交互终端：手动敲 yes
ssh -T git@github.com

# 脚本/非交互：预先采集指纹
ssh-keyscan -t ed25519 github.com >> ~/.ssh/known_hosts

# 临时绕过（仅调试用，会失去指纹校验）
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null git@github.com
```

**知识点**
- `known_hosts` 存的是**主机公钥**，`authorized_keys` 存的是**用户公钥**，两者完全不同：
  - known_hosts → 我信任这台服务器
  - authorized_keys → 这台服务器信任我这个用户
- 服务器重装系统后主机密钥会变，ssh 会警告 `REMOTE HOST IDENTIFICATION HAS CHANGED`——**生产环境不能无脑忽略**，可能是被劫持。处理：`ssh-keygen -R 主机名` 删掉旧记录再连。

**口述 30 秒**
> SSH 双向验证：我用密码/密钥证明"我是谁"，同时用 known_hosts 校验"对面是不是真的那台机器"。前者防冒充用户，后者防中间人。

### 问题 4：22 端口 `Connection timed out`（今日最核心）

**现象**：`ssh -T git@github.com` 卡 1–2 分钟后 `Connection timed out`；换 `-p 443 git@ssh.github.com` 秒通。

**原因**
- SSH 默认走 **22 端口**。国内网络链路对 GitHub 的 22 端口经常阻断/丢包，表现为"一直等到超时"，而非明确拒绝。
- GitHub 官方为此提供**备用 SSH 通道**：`ssh.github.com:443`（用 HTTPS 端口跑 SSH 协议）。

**解决**：写 `~/.ssh/config`（**文件名必须是无后缀的 config**）：
```
Host github.com
  HostName ssh.github.com
  Port 443
  User git
  IdentityFile ~/.ssh/id_ed25519
```
含义：连 `github.com` 这个名字时，实际连接 `ssh.github.com` 的 443 端口。对 `git clone/push` 完全透明，仓库地址不用改。

**知识点**
- **超时 vs 拒绝**：
  - `Connection refused`：对端可达，端口没监听（服务没起 / 被 REJECT）
  - `Connection timed out`：包发出去没回音（被防火墙 DROP / 链路阻断）
- 排查顺序：`ping` → `telnet 主机 端口` / `nc -zv 主机 端口` → 换端口试 → 找官方备用通道。
- ssh 客户端读配置的优先级：命令行参数 > `~/.ssh/config` > 系统级 `/etc/ssh/ssh_config`。
- Windows 下记事本保存会**自动补 `.txt`**，文件名就成了 `config.txt`，ssh 完全不读它——今天正是踩了这个。

**口述 30 秒**
> 超时和拒绝要分清：拒绝说明对端活着但端口没开，超时说明链路被掐。处理上先探端口，再换端口，最后看有没有官方备用通道。GitHub 的 443 SSH 通道就是官方给的备用路径，配在 config 里对上层透明。

### 问题 5：建仓库报 `Something went wrong!`，实际已成功

**现象**：点 Create repository 弹出错误条；刷新重试后提示 `ops-notes already exists in this account`。

**原因**
- 前端报错 ≠ 服务端没执行。请求已写库成功，返回响应时链路出错，页面只看到红条。
- 仓库名在账号下唯一，第二次创建被拒——**这条拒绝恰好证明第一次成功了**。

**解决**：报错后先去仓库列表确认，别盲目重复提交。

**知识点**
- **幂等（Idempotency）**：同一请求执行一次和执行多次，结果一致。GET/PUT/DELETE 天然幂等，POST 通常不是。
- 分布式系统三条铁律：**超时 ≠ 失败**；**重试要有幂等保障**；**先查状态再决定动作**。
- 运维场景：批量重启、批量扩容、批量改配置，脚本里必须"先查当前状态 → 再决定是否执行"。

**口述 30 秒**
> 分布式环境下请求和响应是两件事：请求可能已经生效，只是响应没回来。所以判断成败不能只看有没有报错，要去查实际状态。写自动化脚本时，先查后改，才能安全重跑。

### 问题 6：中文用户名导致 URL 乱码

**现象**：用户名「白夜-2004」，仓库地址显示 `github.com/%E7%99%BD%E5%A4%9C-2004/...`。

**原因**：URL 规范只允许 ASCII 字符，非 ASCII 必须按 **percent-encoding** 转成 `%XX`（UTF-8 字节的十六进制）。中文用户名能用，但所有链接都会变成不可读长串。

**解决**：Settings → Account → Change username → `baikangwei-ops`（英文小写+连字符）。

**知识点**
- `白` 的 UTF-8 是 `E7 99 BD` → URL 编码成 `%E7%99%BD`；`夜` → `%E5%A4%9C`。
- 同类现象：CSV 中文乱码（GBK vs UTF-8）、下载文件名乱码、终端中文乱码——都是编码层不匹配。
- 工程约定：**用户名、仓库名、文件名、变量名一律用 ASCII**。

**口述 30 秒**
> 这是字符编码问题：中文字符在 UTF-8 下占 3 字节，URL 里必须转义成 %XX。日常遇到的乱码，本质都是"某一层用了错误编码"或"该转义没转义 / 不该转义却转了"。

### 问题 7：误建中文文件夹 `操作说明/注释/`

**现象**：想建 `notes/README.md`，结果建成了 `操作说明/注释/README.md`。

**原因**
- GitHub 网页的文件名输入框支持用 `/` 直接建目录（输 `notes/` 就新建 notes 文件夹）。
- 当时用**中文输入法**，输入的字符和斜杠被当成目录名；中文输入法下的 `/` 可能还是全角 `／`，前端当成普通字符。

**解决**：切英文输入法 → 输入 `notes/README.md` → 看面包屑显示 `仓库名 / notes /` 再提交。建错的目录可进入后点 `...` → Delete directory 删除。

**知识点**
- 全角/半角差异：全角字符在字节层面和半角完全不同，程序不认。
- 路径里出现空格、中文、特殊字符，是脚本报"文件找不到"的高频原因。
- 脚本规范：绝对路径、变量加双引号、文件名只用 ASCII。

**口述 30 秒**
> 路径问题最容易被忽略，但排查成本高。约定是：脚本里用绝对路径，变量加引号防空格截断，文件名只用 ASCII。这样能省掉大量莫名其妙的"找不到文件"。
