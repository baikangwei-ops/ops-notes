# 11月27日 · D5

今天做快照实验，计划上就四件事：拍快照、换系统、回滚、释放。活儿本身没什么难的，但中间撞了三个跟"盘"有关的坑，都挺有意思，记一下。

开工先 pull 代码，结果 GitHub 报 `Connection reset by 20.205.243.160 port 443`。我第一反应是 D1 配的那个 443 通道是不是坏了，手都伸向 ssh config 了。停下来又看了一眼报错——那个 IP 就是 GitHub 走 443 的地址，能连到它、走的是 443，说明配置明明在工作，只是连到一半被掐断了。什么都没改，原样重试，第二次就 `Already up to date.`，前后不到两分钟。后来查了一下才把三种"连不上"分清楚：超时是包根本没到，拒绝是到了对方不让进，reset 是连接建起来中途被踹。这种干扰一般几十秒到几分钟自己就好，先重试、再用 `ssh -T` 测通道，别一上来就动配置——配置是对的，乱改反倒把对的改坏。

按计划先把昨天那台北京机器释放了。昨天只敢练到"停止"，今天补上"释放"，列表里实例真的消失、额度也不跳了，这俩的区别昨天只写在纸上，今天算亲手摸到了。然后开新机器，开完才发现它落在杭州不是北京——地域这东西平时没感觉，等以后想让两台机器走内网互通才发现必须同一个地域同一个 VPC，先记着。新机器的安全组得重新配一遍，规则不会跟着实例走。提交时弹了个黄色警告说把 22 对全世界开放会被扫，我想了想点了"我已知悉"——练习机而已，密码够强里面没东西，被扫到也就是日志里多几条爆破记录；但这条在生产环境是真警告，正确做法是把来源锁成公司出口 IP，或者干脆禁掉密码只留密钥。

拍快照之前得先造点数据，不然回滚成没成功根本看不出来。登上去建了个标记文件 `/root/important-data/mark.txt`，然后控制台 → 存储与快照 → 云盘那行 → 创建快照，起名 `d5-练习前-20261127`。它让我选"云盘"还是"实例"，我选的云盘——快照的单位就是盘，一块盘某个时刻的完整照片；选实例那个是一次性给好几块盘拍一致性组，数据库多盘才用得上。进度条从 0 爬到 100% 的工夫我掐了个表。顺带发现快照是按存储量计费的，从那 300 额度里扣，所以它跟实例一样是"用完得清掉"的东西。起名时还手滑把日期写成了 `202611.27`，中间多个点，懒得改了——这事本身就说明台账得回头检查，写错一点点以后找起来就费劲。

换系统那一页藏了四个要动脑子的地方。安全设置默认停在"密钥对"上，那是后面的课，今晚用不上，切到"自定义密码"设了个新的——换系统会重置登录凭证，这条记住。默认还勾了个"免费安全加固"要装常驻安全 agent，跟昨天关掉那个营销弹窗一个道理，学习机保持干净，软件自己手动装才有学习价值。页面顶上一条灰色提示写着"CentOS 已于 2024 年 6 月 30 日全部停服，请尽早制定应对方案"——前几天我还在担心学了老版本面试被嫌弃，好家伙，阿里云自己都挂着这句话了，截图存下来以后就是"版本意识"的现成证据。还有它把系统盘写成 `/dev/xvda`，可我昨天 `lsblk` 看到的是 `vda`，控制台是老模板文案，机器里那个才是真的，这种"控制台说的和机器里实际的不一样"一律以机器为准。接着"停止实例"页又有两组开关：默认勾的是"强制停止"，那是硬断电可能丢数据，我改成普通的"停止"让系统优雅收尾；停止模式保持"普通停机"没动，蓝字明说换系统要用普通模式不然可能启动失败。这里还把昨天那句"停止≠释放"补了一层——按量付费有两种停法，普通停机 CPU 内存照收钱，节省停机算力不收了但盘还收、而且可能因为库存不够起不来、公网 IP 也可能变。

换完系统重新 ssh 上去，`ls /root/important-data` 报 No such file or directory，数据没了，灾难现场成立。按剧本该快照出场救场，结果"回滚云盘"按钮是灰的，点不动。我第一反应是控制台抽风，或者快照没做完，刷新了两遍还是灰。盯着快照列表一行行看，目光落到云盘 ID 上才反应过来——快照属于那块旧盘 `d-bp17d8...`，换系统之后实例挂的是另一串新 ID。原来"更换操作系统"根本不是我以为的清空重装，它是**换了一块全新的系统盘，旧盘被释放**；快照绑的是盘不是实例，旧盘都没了，回滚自然没有对象。旧盘救不回当前机器了，我就在新盘上重来一遍闭环：重建标记文件 → 给这块新盘重拍一个快照 → 这次不换系统，直接 `rm -rf` 删掉标记文件制造灾难 → 对新快照回滚 → `cat mark.txt`，那行字回来了。这么一折腾反倒白捡了两组对照：换系统那种灾难盘换了、快照救不回当前实例，删除那种灾难盘还在、快照直接回滚。还有条进阶路线先记账上——旧快照其实没废，用它的"创建自定义镜像"做成镜像，再拿镜像换系统，旧盘那套状态连 mark.txt 一起能以新盘形式回来，这是跨盘恢复的正解，留给周日验收日玩。

回滚前收到提醒说"回滚后密码会退回拍快照那一刻的旧密码，先用旧密码试"，我照着试了好几次原来的密码，全登不上。我以为回滚真把密码时光倒流了，越试越懵。卡了一会儿干脆不想密码本身，改想密码到底存在哪——Linux 密码存在系统盘的 `/etc/shadow` 里，一串哈希；回滚是整块盘退回快照那一刻，shadow 也跟着退，可这次是**同盘回滚**，盘从头到尾没换过，shadow 根本没动，前后当然是同一个密码。坏就坏在我把两组实验混了：换系统那次盘换了、密码跟着新盘变，这次盘没换、密码没变，我拿着前一次的结论去套后一次。用那个一直没变的密码直接就登上了，根本没有"切换密码"这回事。一句话钉死：**密码跟盘走，不跟实例走，也不跟快照走。** 顺带把两个老问题一起解决了——控制台"重置密码"为什么要重启生效，因为重置是去改盘上的 shadow，sshd 要重启才重新读；为什么不能把别的盘的 shadow 直接搬过来，哈希带各盘自己的盐，搬过去也对不上。

今天这三个坑入口不一样，一个是网络、一个是存储、一个是认证，但卡住我的地方是同一类：拿着本地的老经验往云上套，套不通才逼着去想底层到底是什么。git 配置、格式化重装、密码存在"某个后台"，这些想当然全是错的，真相都得落到"它物理上存在哪、跟着什么走"才能解释清楚。下次再遇到"我以为它会这样结果不是"，先别急着试，先问一句：这东西到底存在哪？
