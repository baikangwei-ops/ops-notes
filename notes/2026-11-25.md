# 2026-11-25 · D3

按昨晚立的规矩，开工第一件事 `git pull`。结果这条命令直接把我送进一个看不懂的界面，光标停在中间，敲什么都没反应——昨晚明明记着要用 `pull --rebase`，今天偏偏敲成了 `git pull`。不过事后看，这一天反而是三天里收获最大的一天。

先把昨天的欠账补上。昨天日记里写"`git diff` 还没真跑过"，今天就拿它开刀。故意在 README 里加了一行字，然后依次跑 `git diff`（看到新加的那行）→ `git add README.md` → 再 `git diff`（这次什么都没输出）→ `git diff --staged`（改动又出现了）→ `git commit` → `git diff HEAD`（没输出，工作区和仓库一致了）。最有意思的是中间那次 `git diff` 突然没输出——昨天这时候我会误判成失败，今天自己就反应过来了：文件已经 add 进暂存区，工作区和暂存区没差异，diff 自然没话说。三个 diff 的分工也就清楚了：`git diff` 看我还没挑的改动，`git diff --staged` 看已经挑进篮子的，`git diff HEAD` 是全部改动的总账。

写今日笔记前那次 `git pull` 出了岔子。本地和远端的分叉需要合并，git 弹出 vim 让我写合并说明。屏幕整个变了样：顶部一行 Merge 开头的英文，中间波浪线，底部一堆 `#` 注释，键盘敲字母没反应。第一反应是"完了，敲坏了什么"。其实它是在等我写合并说明，敲字母没反应是因为 vim 默认在普通模式、不是打字模式。逃生三步是 `Esc` → `:wq` → 回车，接受默认说明就合并完了。事后 `git log` 一看，历史里多了一条 `Merge branch 'main' of ...`，这就是昨天说的"不加 --rebase 会多出 Merge 记录"，今天亲眼见到了。以后固定用 `pull --rebase`。今天还发现这事儿和昨天 echo 没输出是同类问题的变体——**不是失败，是它在等输入**，只是换了个界面我没认出来。屏幕安静至少有几种可能：成功、等输入、真失败，判断方法各不相同，不能一概而论。

不过今天真正的转折不在命令上。三天下来 add/commit/push 能跑通，但说句实话：我到现在也没看懂那些命令在干什么。感觉 git 的命令和 linux 完全是两套逻辑——linux 的命令我能猜功能（ls 是列、cp 是复制），git 的命令一个都猜不出来，我一度怀疑是不是自己不适合学这个。后来把三天串起来看，发现问题不在练得够不够，在于心里没有地图：我知道每条命令怎么敲，但不知道它们在 git 内部动了什么，等于闭着眼睛背路。linux 我学得动，是因为每条命令动的是看得见的文件和目录。

所以今天把分支和 reset 往后推了，改成去补地图——把廖雪峰的 git 教程前三章边看边敲过一遍，重点不是学新命令，是搞清楚每条命令动了哪个区。看完再回头看这三天的日记，之前的命令全对上号了：add 是工作区到暂存区，commit 是暂存区到本地仓库，push 是本地仓库到远端，pull 反过来。原来缺的不是重复，是模型。

顺手琢磨了个问题：分支是不是类似 linux 的子目录？自己推了一圈，答案是不是，而且这个类比很骗人。子目录是盒子，文件真装在里面，`cd` 进去看到的就是盒里的东西；分支是便签，只是一个 41 字节的指针文件（`.git/refs/heads/main`），上面写着某个 commit 的编号，它不装任何东西。`git switch -c dev` 创建新分支只花一瞬，磁盘上就多一个 41 字节文件——如果真像建子目录要搬一堆文件，不可能这么快。更贴切的类比是游戏存档：commit 是存档点，分支是"我当前站在哪个存档上"的标记，切分支就是切存档，整个工作区会跟着变成那个存档时的样子。这个理解留到周六学分支实操时验证，对得上就算提前啃下来了。
