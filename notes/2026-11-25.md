按昨晚定下的规矩，开工第一件事 `git pull`。结果这条命令直接把我送进了一个看不懂的界面，光标停在中间，敲什么都没反应——昨晚明明说过用 `pull --rebase`，我今天偏偏忘了。不过事后看，这一天反而是三天里收获最大的一天：diff 三连补完了，而且我第一次弄明白了 git 整体的"地图"。

## 今日新掌握的命令

**git 部分**

| 命令 | 干什么 | 关键点 | 要不要背 |
|---|---|---|---|
| `git diff` | 对比**工作区**和**暂存区**的差异 | `+` 是新增行，`-` 是删除行；刚改完还没 add 时用它看自己改了啥 | **必背** |
| `git diff --staged` | 对比**暂存区**和**上一次 commit** 的差异 | add 之后想检查"我到底挑了什么进存档"，用它 | **必背** |
| `git diff HEAD` | 对比**工作区**和**最后一次 commit** 的差异 | 全部改动的总账，add 没 add 都算在内 | **必背** |
| `git pull` | fetch + merge，拉远端并合并 | 远端分叉时会弹 vim 让你写合并说明，新手容易卡死 | 必背，但**日常用 `pull --rebase`** |
| `git merge --abort` | 放弃一次正在进行的合并，回到合并前状态 | 合并弄乱了救命用（今天知道了，还没实战用过） | 记住，救命用 |
| `git log --graph --oneline` | 带分支线图地看提交历史 | 看历史有没有分叉、合并，一眼看出来 | 必背 |

**vim 逃生键（今天被迫学会的）**

| 按键 | 干什么 | 关键点 |
|---|---|---|
| `Esc` 然后输入 `:wq` 回车 | 保存并退出 vim | 卡在 vim 里就这三步，不用慌 |
| `Esc` 然后输入 `:q!` 回车 | **不**保存强行退出 | 改乱了不想留，用这个 |

> vim 不是今天的正课，是被合并界面逼出来的。但这个逃生技能必须记住：**只要屏幕左下角出现插入提示或光标停在奇怪的位置，先按 Esc，再敲 `:q!`，天塌不下来。**

## 19:30 补昨天的欠账：diff 三连

昨天日记里写了"`git diff` 还没真正跑过"，今天第一件事就是它。我故意在 README 里加了一行字，然后依次跑：

```
git diff              # 看到 + 我加的那行（绿色/带+号）
git add README.md
git diff              # 没输出了！
git diff --staged     # 改动又出现了
git commit -m "docs: 练习 diff"
git diff HEAD         # 没输出，工作区和仓库一致了
```

最有意思的是中间那次 `git diff` 什么都没输出——我以为坏了，后来想明白：文件已经 add 进暂存区了，工作区和暂存区**没有差异**，diff 自然没话说。这是第二次碰到"没输出"，但这次我自己就反应过来了，没像昨天那样误判成失败。

所以 diff 三连的分工我总结成一句话：

- `git diff`：看我**还没挑**的改动
- `git diff --staged`：看我**已经挑进篮子**的改动
- `git diff HEAD`：全部改动总账

## 19:50 被 git pull 送进了 vim

写今天的笔记前，我按规矩先 `git pull`——但敲成了 `git pull`，不是 `git pull --rebase`。本地和远端的分叉（昨天补的 README 之类和我本地没推的东西）需要合并，git 于是弹出 vim，让我写合并提交的说明。

当时屏幕整个变了样：顶部一行 Merge 开头的英文，中间波浪线，底部一堆 `#` 开头的注释，键盘敲字母没反应。我第一反应是"完了，敲坏了什么"。

实际发生的事：

1. 这是 vim 编辑器，在等**我**写合并说明
2. 敲字母没反应是因为 vim 默认是"普通模式"，不是打字模式
3. 逃生三步：`Esc` → 输入 `:wq` → 回车，接受默认说明，合并完成

合并完 `git log --oneline` 一看，历史里多了一条 `Merge branch 'main' of ...`——这就是昨晚说的"不加 --rebase 会多出一条 Merge 记录"，今天亲眼见到了。以后固定用 `git pull --rebase`，不再让历史长岔子。

## 20:15 学不动了，我怀疑 git 的问题出在我身上

三天下来 add/commit/push 能跑通，但说一句实话：**我到现在也没看懂那些命令在干什么**。感觉 git 的命令和 linux 完全是两套逻辑，linux 的命令我能猜出功能（ls=列、cp=复制），git 的命令一个都猜不出来。我一度怀疑是不是自己不适合学这个。

后来把这三天串起来看，我发现问题不在重复次数，在于**我心里没有地图**：我知道每条命令怎么敲，但不知道它们在 git 内部动了什么，等于闭着眼睛背路。linux 我学得动，是因为每条命令动的是看得见的文件和目录。

所以今天把分支和 reset 往后推了，改成去补地图：把廖雪峰的 git 教程前三章边看边敲过一遍（入门→工作区暂存区→时光机），重点不是新命令，是搞清楚**每条命令动了哪个区**。看完再回头看这三天的日记，之前的命令全部能对上号了：

- `add` = 工作区 → 暂存区
- `commit` = 暂存区 → 本地仓库
- `push` = 本地仓库 → 远端
- `pull` = 远端 → 本地仓库 → 合并进工作区

## 顺手问了一个问题：分支是不是类似 linux 的子目录？

不是。这个类比骗人，我自己推出来的结论是：

- **子目录是盒子**：文件真的装在里面，`cd` 进去看到的就是盒里的东西
- **分支是便签**：只是一个 41 字节的指针文件（`.git/refs/heads/main`），上面写着某个 commit 的编号，**它不装任何东西**

`git switch -c dev` 创建新分支，磁盘上只多了一个 41 字节的文件，快得不像话——如果是建子目录要搬一堆文件，不可能这么快。更像的类比是**游戏存档**：commit 是存档点，分支是"我当前站在哪个存档上"的标记，切分支就是切换存档，整个游戏世界（工作区文件）会跟着变成那个存档时的样子。

这个理解周六学分支实操时验证，如果对得上，分支就算提前啃下来了。

## 今天弄明白的几个概念

**我原以为 git pull 卡住是出故障了，其实是 git 在 vim 里等我写合并说明**——连续两天遇到"没反应"，一次是静默成功，一次是在等输入，说明"屏幕安静"至少有三种可能：成功、等输入、真失败。判断方法各不相同，不能一概而论。

**diff 三连对应三个比较对象**：工作区、暂存区、最后一次提交。diff 的本质就是"拿两个东西比"，命令只是指定比谁和谁。

**缺地图 vs 缺重复**：学不动不一定是练得不够，可能是心里没有整体模型。先补模型再练，每条命令就不再是孤立的咒语。

**pull 默认是 merge**：会产生合并提交；`pull --rebase` 是把本地提交搬家到远端之后，历史保持直线。日常固定后者。
