## 19:45 建文件，但它"没反应"

```
echo "# 11月24日" > notes/2026-11-24.md
```

回车，什么都没发生，直接回到提示符。我以为没建成，去文件夹里翻也没看出变化。

问了才知道这是 Linux 的老规矩：**成功不吭声，出错才说话**。验证要靠命令，不靠肉眼：

```
ls notes/                 # 文件在
cat notes/2026-11-24.md   # 内容对
git status                # 红色 untracked: notes/2026-11-24.md
```

看到那行红色 untracked 才算真正确认：文件建好了，git 已经看见它，但还没跟踪。这句"验证靠命令不靠肉眼"，比今天学的六个命令都值钱——以前我盯着屏幕等回显，现在知道该敲什么去问。

## 20:29 push 被拒了两次

add、commit 都顺利，`git push` 直接红字：

```
! [rejected]  main -> main (fetch first)
error: failed to push some refs
hint: Updates were rejected because the remote contains work that you do not have locally.
```

第一次我没细看 hint，直接又 push 了一次，还是同样的报错。

读懂那句话才明白：**远端有我本地没有的提交**。原因就是 19:39 那个"省一步"——我用的旧目录里没有昨晚之后推上去的内容（昨晚后来补的 README 导读、INDEX 索引、故障案例库，还有我自己在网页上改的东西）。

解决三步：

```
git pull --rebase   # 先同步，把我的提交搬到远端最新之后
git log --oneline   # 看清多出来的提交是什么
git push            # 这次通过了
```

`git pull --rebase` 的意思是：先把远端的新提交拉下来，再把我本地的新提交"搬家"到它们后面，历史保持一条直线。如果只 `pull` 不加 `--rebase`，会多出一条 "Merge branch..." 的合并记录，看着乱。

这一步弄懂的道理：**push 被拒不是坏事，是 git 在拦着你别覆盖别人的东西**。以后多人协作，顺序永远是"先 pull 再 push"。

## 今天还有一个此前没意识到的坑

我中间在 GitHub 网页上改过 README，还建过一个 `Add notes for Git commands` 的提交，后来又把 `2026-11-24.md` 删掉重建。当时只当成"改网页文件"，没意识到——**网页上点一次 Commit changes，就是往远端提交一次**，本地完全不知情。这正是我 push 被拒的另一个来源：远端被我自己的网页操作推前了。

## 今天弄明白的几个概念

**git 的四层结构**：工作区（我在编辑的文件）→ 暂存区（add 之后）→ 本地仓库（commit 之后）→ 远端（push 之后）。add 不是"保存"，是"挑选"——一个仓库改了 5 个文件，可以只挑 2 个进下一次存档。commit 只存在我电脑上，push 完才有云端备份。

**commit 说明的写法**：行业习惯是 `类型: 说明`，比如 `notes:`、`fix:`、`docs:`。这些东西以后面试官会翻，写清楚比写多重要。

**命令的通用结构**：`工具 → 选项 → 操作对象`。`chmod -R 755 目录`、`git commit -m "说明"` 都是这个结构。看清空格位置，遇到陌生命令能猜出一半。

**pull 和 push 是一对**：一个往里拿，一个往外推。每天都该先 pull 再动手，收工再 push。
