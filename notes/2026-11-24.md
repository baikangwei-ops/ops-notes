昨天配好了密钥和仓库，今天该真正用一遍 git 了。计划的 D2 写得很简单：add / commit / push / log / diff 走一遍，把攒的笔记放进仓库，写个 .gitignore。我以为是半小时的事，结果从 19:15 弄到 20:40，中间卡了两次。

## 今日新掌握的命令

**git 部分（九个，前六个必须脱稿）**

| 命令 | 干什么 | 关键点 | 要不要背 |
|---|---|---|---|
| `git config --global user.name "名字"` | 设置提交时记录的作者名 | 存在 `~/.gitconfig`；去掉 `--global` 只对当前仓库生效 | 不用，配一次终身有效 |
| `git config --global user.email "邮箱"` | 设置提交作者邮箱 | **必须和 GitHub 账号绑定的邮箱一致**，否则提交不算到你的贡献记录里 | 不用，但邮箱别填错 |
| `git clone <仓库地址>` | 把远端仓库完整拉到本地（含全部历史），并自动建立 `origin` 关联 | 目录已存在会报错，不能重复 clone | **必背** |
| `git status` | 看当前状态：红的未跟踪/未暂存，绿的已暂存，还会告诉你本地领先或落后远端几条 | 无副作用，迷路就敲它 | **必背**，用得最多 |
| `git add <路径>` / `git add .` | 把改动挑进暂存区 | `.` 是全部；add 是"挑选"不是"保存" | **必背** |
| `git commit -m "类型: 说明"` | 把暂存区打包成一次存档，生成 commit id | 不加 `-m` 会弹编辑器，新手容易卡在里面 | **必背** |
| `git push` | 把本地的新提交上传到远端 | 报 `rejected (fetch first)` = 远端有你没有的提交，先 pull | **必背** |
| `git pull --rebase` | 拉远端新提交，再把本地提交"搬家"到它们后面，历史保持一条直线 | 不加 `--rebase` 会多出一条 Merge 记录 | **必背** |
| `git log --oneline` | 一行一条看提交历史 | 缩略 id 可以用来回滚、对比 | 必背 |
| `git diff` | 对比工作区和暂存区的差异，`+` 是新增行、`-` 是删除行 | 只看了说明，**还没真正跑过** | 要背，明天补跑 |

**系统与 shell 部分（今天顺手用到的）**

| 命令 | 干什么 | 关键点 |
|---|---|---|
| `ssh -T git@github.com` | 测试 SSH 能不能通过 GitHub 认证 | `-T` = 不分配终端，只要能认证就行 |
| `cd $env:USERPROFILE\.ssh` | PowerShell 里进 `.ssh` 目录 | `$env:变量名` 是 PowerShell 读环境变量的写法，等价于 Linux 的 `$HOME` |
| `Rename-Item config.txt config` | PowerShell 改文件名 | 用来把记事本偷偷加上的 `.txt` 去掉 |
| `echo "内容" > 文件` | 把内容写进文件，`>` 覆盖、`>>` 追加 | 成功时**没有任何输出**，要用 `ls`/`cat` 验证 |
| `ls` / `cat` / `cd` | 列目录 / 看文件内容 / 进目录 | 命令行三件套，验证产物全靠它们 |
| 安装器加 `/VERYSILENT /NORESTART` | 静默安装、装完不自动重启 | Inno Setup 打包的 Windows 软件通用 |

> 从今天起每篇日记都留这一节，攒到 3 月就是一本自己写的命令手册——面试前翻它，比翻任何教程都快。

## 19:45 建文件，但它"没反应"

```
echo "# 11月24日" > notes/2026-11-24.md
```

回车，什么都没发生，直接回到提示符。我以为没建成，去文件夹里翻也没看出变化。

问了才知道这是 Linux 的老规矩：**成功不吭声，出错才说话**。验证要靠命令，不靠肉眼：

```
ls notes/                 # 文件在
cat notes/2026-11-24.md   # 内容对
git status                # 红色 untracked: notes/2026-11-24.md
```

看到那行红色 untracked 才算真正确认：文件建好了，git 已经看见它，但还没跟踪。这句"验证靠命令不靠肉眼"，比今天学的六个命令都值钱——以前我盯着屏幕等回显，现在知道该敲什么去问。

## 20:29 push 被拒了两次

add、commit 都顺利，`git push` 直接红字：

```
! [rejected]  main -> main (fetch first)
error: failed to push some refs
hint: Updates were rejected because the remote contains work that you do not have locally.
```

第一次我没细看 hint，直接又 push 了一次，还是同样的报错。

读懂那句话才明白：**远端有我本地没有的提交**。原因就是 19:39 那个"省一步"——我用的旧目录里没有昨晚之后推上去的内容（昨晚后来补的 README 导读、INDEX 索引、故障案例库，还有我自己在网页上改的东西）。

解决三步：

```
git pull --rebase   # 先同步，把我的提交搬到远端最新之后
git log --oneline   # 看清多出来的提交是什么
git push            # 这次通过了
```

`git pull --rebase` 的意思是：先把远端的新提交拉下来，再把我本地的新提交"搬家"到它们后面，历史保持一条直线。如果只 `pull` 不加 `--rebase`，会多出一条 "Merge branch..." 的合并记录，看着乱。

这一步弄懂的道理：**push 被拒不是坏事，是 git 在拦着你别覆盖别人的东西**。以后多人协作，顺序永远是"先 pull 再 push"。

## 今天弄明白的几个概念

**git 的四层结构**：工作区（我在编辑的文件）→ 暂存区（add 之后）→ 本地仓库（commit 之后）→ 远端（push 之后）。add 不是"保存"，是"挑选"——一个仓库改了 5 个文件，可以只挑 2 个进下一次存档。commit 只存在我电脑上，push 完才有云端备份。

**commit 说明的写法**：行业习惯是 `类型: 说明`，比如 `notes:`、`fix:`、`docs:`。这些东西以后面试官会翻，写清楚比写多重要。

**命令的通用结构**：`工具 → 选项 → 操作对象`。`chmod -R 755 目录`、`git commit -m "说明"` 都是这个结构。看清空格位置，遇到陌生命令能猜出一半。

**pull 和 push 是一对**：一个往里拿，一个往外推。每天都该先 pull 再动手，收工再 push。
