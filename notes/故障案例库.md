## C001　SSH 连 GitHub 一直超时

**环境**：Windows 10/11 + PowerShell（Windows OpenSSH），目标 `github.com`

**现象**

`ssh -T git@github.com` 无任何输出，卡一分多钟后报：

```
ssh: connect to host github.com port 22: Connection timed out
```

**排查过程**

1. 先怀疑断网 → `curl -I https://github.com` 正常返回 200，排除网络完全不通
2. 怀疑密钥问题 → 但密钥错误会报 `Permission denied (publickey)`，不会超时，排除
3. 判断是端口层面：22 端口连通性被阻断/丢包
4. 查 GitHub 官方文档，确认提供备用 SSH 通道 `ssh.github.com:443`
5. 验证：`ssh -T -p 443 git@ssh.github.com` → 立即返回 `Hi baikangwei-ops!`
6. 结论成立，写进 `~/.ssh/config` 固化

**根因**

GitHub 的 SSH 服务监听 22；部分网络链路对 22 端口做阻断，表现为 SYN 无响应（超时），而不是拒绝。

**修法**

```
# ~/.ssh/config
Host github.com
  HostName ssh.github.com
  Port 443
```

**预防 / 经验**

- 超时和拒绝是两类问题：`refused` = 端口没开，`timed out` = 链路被掐
- 探端口用 `telnet 主机 端口` 或 `nc -zv 主机 端口`
- 大厂/开源项目一般都有备用通道（443、80），先查文档再折腾网络

**面试怎么说（30 秒）**

> 我用 SSH 连 GitHub 时一直超时，但 curl 网页是通的，说明不是断网，是端口层面的问题。SSH 默认走 22，22 被链路阻断就会这样。GitHub 官方提供了 443 的备用通道，我用 -p 443 连 ssh.github.com 验证通过，然后把它写进 ssh config，对 git 命令就透明了。

## C002　ssh 配置文件写了不生效

**现象**

按文档写了 `~/.ssh/config`，但 `ssh -T git@github.com` 仍然走 22、仍然超时。

**排查过程**

1. `ls -la ~/.ssh/` 发现文件叫 `config.txt`，不是 `config`
2. 原因：Windows 记事本保存时自动补 `.txt` 后缀
3. 改名后重测，走 443 正常

**根因**

ssh 只读取固定文件名 `~/.ssh/config`，带后缀的文件不解析；Windows 默认隐藏已知扩展名，容易看不出来。

**修法**

```
cd $env:USERPROFILE\.ssh
Rename-Item config.txt config
```

**预防 / 经验**

- Windows 上改配置文件，先关掉"隐藏已知文件类型的扩展名"
- 改任何配置后都要验证生效，不能假设"写了就等于生效"

## C003　建仓库报错，其实已经创建成功

**现象**

GitHub 点 Create repository，页面弹红色 `Something went wrong!`；刷新重试后提示：

```
ops-notes already exists in this account
```

**排查过程**

1. 第一次以为失败，直接重试
2. 提示"已存在"，说明第一次其实成功了
3. 去仓库列表确认，仓库确实在

**根因**

请求已送达服务端并写入成功，返回响应时链路出问题，前端只能显示失败。服务端的行为是成功的。

**修法**

不用修，先去确认状态。后续操作前先查（`git ls-remote`、列表页）。

**预防 / 经验**

- 分布式系统里"超时 ≠ 失败"，重试前先查状态
- 写自动化脚本时注意幂等：先查后改，避免重复创建/重复执行

## C004　git push 被拒（fetch first）

**环境**：Windows + Git Bash 2.56，本地仓库是前一天 clone 的副本

**现象**

`git add` / `git commit` 都正常，`git push` 直接报错：

```
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:baikangwei-ops/ops-notes.git'
hint: Updates were rejected because the remote contains work that you do not have locally.
```

**排查过程**

1. 第一反应是网络抖动，直接又 push 一次 → 报错完全一样，排除偶发网络问题
2. 读 hint 那句 `the remote contains work that you do not have locally` → 意思是远端有本地没有的提交
3. `git log --oneline` 看本地：只有自己刚才那条提交
4. `git fetch origin` 后看 `git log --oneline origin/main`：远端多出好几条——之前补的 README 导读、INDEX 索引、故障案例库，还有我自己在网页上点出来的两条 `Update README.md`
5. 确认根因：本地这份仓库是前一天 clone 的，之后远端一直被推前，本地一直没同步
6. 解决：`git pull --rebase` → `git log --oneline` 确认自己的提交排在最新之后 → `git push` 通过

**根因**

git 的推送是"快进"模型：远端分支必须是你本地历史的后代，否则会把别人（或别的设备）的提交覆盖掉，所以 git 直接拒绝。本地落后于远端时，push 一定被拒，跟网络没关系。

**修法**

```
git pull --rebase origin main   # 拉远端，把自己的提交搬到最新之后
git log --oneline               # 确认历史
git push                        # 再推，通过
```

**预防 / 经验**

- 每天开工第一件事 `git pull`，收工最后一件 `git push`
- 不要在网页上编辑同一个仓库——网页每点一次 Commit changes，就是一次远端提交，本地完全不知情
- 看到 `rejected` 先读 hint 再动手，不要连续重试
- 不要用 `--force`：那等于把别人的提交删掉，多人协作里这是事故

**面试怎么说（30 秒）**

> 我本地 clone 了仓库，第二天改完 push 被拒，报 fetch first。看 hint 说的是远端有本地没有的提交，我用 git log 对比本地和 origin/main，发现远端多了几条——包括我自己在网页上编辑产生的提交。原因是本地那份是旧的，一直没同步。用 pull --rebase 把提交变基到最新之后，再 push 就通了。之后我改了习惯：开工先 pull，收工再 push，也不再在网页上直接改仓库。

## C005　命令执行后没有任何输出，误判为失败

**现象**

```
echo "# 11月24日" > notes/2026-11-24.md
```

回车后直接回到提示符，屏幕上什么都没多。去文件夹里翻也没看出变化，以为文件没建成，怀疑是路径写错了。

**排查过程**

1. `ls notes/` → `2026-11-24.md` 在里面，文件其实已经建好了
2. `cat notes/2026-11-24.md` → 输出 `# 11月24日`，内容也对
3. `git status` → 红色 `untracked: notes/2026-11-24.md`，git 也看见了
4. 结论：命令成功，只是它本来就不输出东西

**根因**

Unix 的惯例是"没有消息就是好消息"：命令只在出错时往 stderr 写东西，成功时保持安静。`>` 重定向是把内容写进文件，不是打印到屏幕，所以屏幕上自然什么都没有。

**修法 / 怎么验证**

不要靠眼睛等回显，用命令去问：

```
ls 文件路径      # 产存在吗
cat 文件路径     # 内容对吗
echo $?          # 上一条命令的退出码，0 = 成功
```

**预防 / 经验**

- 判断命令是否成功，看**退出码**和**产物**，不看有没有输出
- `>` 覆盖、`>>` 追加，写之前先确认用哪个，`>` 用错会把原文件清空
- 这条习惯能平移到所有场景：启动服务后 `ps`/`ss` 验证、改配置后重新加载验证、脚本里每一步 `set -e` 兜底

**面试怎么说（30 秒）**

> 我刚开始用重定向建文件，敲完发现屏幕上什么都没有，以为失败了。其实是 Linux 的惯例——成功不输出，出错才输出。正确的验证方式是用 ls、cat 看产物，或者看退出码 echo $?。这件事之后我改了一个习惯：任何操作都用命令去验证结果，而不是凭感觉判断它有没有生效。

## C006　git pull 后屏幕被 vim 占据，键盘"没反应"

**环境**：Windows + Git Bash 2.56，本地与远端存在分叉提交

**现象**

按"开工先 pull"的规矩执行 `git pull`（忘了加 `--rebase`），屏幕突然整个变成另一种界面：顶部一行 `Merge branch 'main' of ...` 开头的英文，中间波浪线，下方一堆 `#` 开头的注释行，光标停在中间。敲字母屏幕不动，像终端卡死了。

**排查过程**

1. 第一反应是命令敲坏了或者终端挂了 → 但窗口还在接收按键（只是没显示），不是死机
2. 认出界面左下角的特征，这是 vim 编辑器
3. 读顶部文字：git 在让我**写这次合并提交的说明**，`#` 开头的行是注释不会生效
4. 敲字母没反应是因为 vim 默认处于"普通模式"，不是输入模式，这是 vim 的机制不是故障
5. 处理：`Esc` → 输入 `:wq` → 回车，接受默认合并说明，退出 vim
6. `git log --oneline` 确认：历史里多了一条 `Merge branch 'main' of ...` 合并提交，本地远端已同步

**根因**

`git pull` 默认是 fetch + merge。当本地和远端的提交出现分叉（都有对方没有的提交）时，merge 会创建一个合并提交，并弹出编辑器（默认 vim）让用户写说明。不了解 vim 的人会把这个编辑器界面误判为"卡死"。

**修法**

卡在合并界面时的逃生三步：

```
Esc        # 确保在普通模式
:wq 回车   # 保存默认说明并退出，合并继续
```

不想留合并提交的话，用 `:q!` 强退后 `git merge --abort` 放弃本次合并。

**预防 / 经验**

- 日常拉代码固定用 `git pull --rebase`：不产生合并提交，不弹编辑器，历史保持直线
- 屏幕突然变化不等于故障。到今天为止"屏幕安静/异常"已有三种可能：静默成功（C005）、git 在等输入（本条）、真出错——判断方法各不同，先认界面再动手
- vim 只需要会两个操作：`:wq` 保存退出、`:q!` 不保存退出。这两个先背下来，等以后真学 vim 再深入
- 合并提交进了历史不影响使用，但不干净；提交历史是给面试官看的，尽量保持直线

**面试怎么说（30 秒）**

> 我有一次 git pull 之后屏幕突然变成另一种界面，敲键盘没反应，一开始以为终端挂了。后来认出那是 vim——因为本地和远端有分叉提交，pull 默认走 merge，弹出编辑器让我写合并说明，而 vim 默认在普通模式所以敲字母没反应。用 :wq 接受默认说明就正常退出了。之后我固定改用 git pull --rebase，不产生合并提交，也不会再弹编辑器。这件事让我养成一个习惯：界面突然变化先分辨"是出错还是在等输入"，不急着乱敲。

## C007　云服务器 ssh 突然超时，机器其实是我自己关的

**环境**：Windows Git Bash → 阿里云 ECS（CentOS 7.9，北京 region，公网 IP）

**现象**

刚 ssh 登录成功，在会话里执行 `hostnamectl set-hostname` 改主机名，想验证效果，敲了 `poweroff`。终端随即“卡死”，敲什么都没反应；关掉终端重新 `ssh root@IP`，报：

```
ssh: connect to host 112.126.89.92 port 22: Connection timed out
```

**排查过程**

1. 第一反应：安全组配错了（刚学的“超时 = 端口不通”，且 C001 也是超时）
2. 回控制台看安全组入方向规则：允许 / TCP / 22/22 / 0.0.0.0/0，规则正确，排除
3. 再想 `Permission denied` 才是密码错，`Connection refused` 才是服务没起，这次是 `timed out`——包根本没到机器
4. 回到实例列表看状态：**已停止**。根因确定
5. 点「启动」，等状态变“运行中”，再 ssh 登录成功，`hostname` 显示新名字（说明改主机名本身没白改）

**根因**

`poweroff` 是关机命令，实例被正常关闭。终端“卡死”是因为本地终端还在，但对面的机器已经下线，连接随系统一起断了——不是终端故障。云上关机后没有“VMware 窗口”可以点“开启”，机器会一直停在停止状态，直到回控制台手动启动。

**修法**

控制台 → 实例列表 → 启动 → 等“运行中” → 重新 ssh。

**预防 / 经验**

- 想重启用 `reboot`（掉线一分钟自己回来）；只有当天彻底收工才用 `poweroff`
- **终端“卡住不动”先查对面机器死活**：`ping` 或控制台看实例状态，别狂敲键盘、别急着重装
- 超时的三层排查：目标是否在线（本案例）→ 链路/安全组是否放行（C001）→ 服务是否监听（`ss -lntp`）
- 停止 ≠ 释放：停止仍在占资源和扣额度，释放才是删除
- 换环境后老习惯的“兜底”会消失：本地虚拟机关机能点窗口再开，云上不能

**面试怎么说（30 秒）**

> 我在云服务器上改完主机名，习惯性敲了 poweroff 想重启，结果终端卡住、重连报超时。第一反应是安全组，检查规则是对的；后来发现实例状态是“已停止”——是我自己关的机。这件事让我总结出一条超时排查顺序：先确认目标在线，再看链路和安全组，最后看服务是否监听。另外我把习惯改了：想重启用 reboot，poweroff 只在真正收工时用，因为云上没有本地虚拟机那种“点一下就开机”的兜底。

## C008　git pull 报 Connection reset by 20.205.243.160 port 443

**环境**：Windows Git Bash，`git pull --rebase`，走 D1 配好的 ssh.github.com:443 通道

**现象**

开工第一步 `git pull --rebase` 报：

```
Connection reset by 20.205.243.160 port 443
fatal: Could not read from remote repository
```

**排查过程（含走错的路）**

第一反应是“D1 配的 443 通道坏了”——差点去改 ssh config。转念一想：`20.205.243.160` 正是 GitHub 走 443 的服务器地址，能解析到这个 IP、连的是 443，说明**配置正在工作**，只是连接中途被掐断。分清楚三种“连不上”：

- `timed out`：包没到，链路不通（C001）
- `refused`：到了但对方拒绝
- `reset`：通道建立了，中途被掐断 ← 本次

**根因**

国内网络访问 GitHub 的临时性干扰，与本地配置无关。reset 是中间设备（而非目标主机）Reset 了连接，通常几十秒到几分钟自己恢复。

**修法 / 预防**

1. 原样重试 2-3 次（本次重试第二次就 `Already up to date.`）
2. 仍失败用 `ssh -T git@github.com` 单独测通道——能出 `Hi xxx! You've successfully authenticated` 就是通道活着，回来再 pull
3. 持续 reset 超过 5 分钟 → 换手机热点（换网络出口最有效）
4. 别动 ssh config——配置是对的，路只是暂时堵了

**面试怎么说（30 秒）**

> 我拉代码时遇到过 Connection reset，不是超时也不是拒绝。我的判断方法是先区分三类错误：超时是链路不通、拒绝是对方拒绝、reset 是连接中途被掐断。看到 IP 和端口是 GitHub 的 443，说明我配的通道在工作，问题在网络波动。重试两次就好了；如果不行我会用 ssh -T 单独测认证通道，再不行就换网络出口。我没有去改配置——因为配置是对的，乱改反而引入新问题。

## C009　更换操作系统后，快照的“回滚云盘”按钮是灰的

**环境**：阿里云 ECS，先对系统盘拍快照，再“更换操作系统”，随后想回滚

**现象**

换系统后数据按预期消失了，打开快照列表准备回滚，发现目标快照操作列的“回滚云盘”是灰色，点不动。

**排查过程（含走错的路）**

一开始以为是控制台 bug 或快照没做完。对着列表看云盘 ID 才反应过来：快照属于那块**旧盘** `d-bp17d8...`，而换系统之后实例挂的是**另一块新盘**。我原以为“更换操作系统 = 清空重装”，实际它**直接换了一块全新的系统盘，旧盘被释放**。快照绑的是盘，源盘没了，回滚就没有对象。

**根因**

快照与云盘绑定，不是与实例绑定。更换操作系统 = 换新盘 + 释放旧盘 → 旧盘上的快照失去回滚目标。

**修法 / 预防**

1. **当晚的补救**：在新盘上重建标记文件 → 对新盘重新拍一个快照 → 用 `rm -rf` 模拟灾难（不动系统）→ 对**新快照**回滚 → 数据复活。同盘回滚完全可用。
2. **进阶路线（跨盘恢复正解）**：旧快照 → “创建自定义镜像” → 用该镜像更换操作系统 → 旧盘完整状态以新盘形式回来。这是“快照可以做成镜像”的实操版。
3. 记住机制：要回滚，先确认**快照的源盘还在不在**；换系统前想清楚——它会让旧盘的所有快照对当前实例失效。
4. 相关：换系统同时会重置登录凭证（见 C010）。

**面试怎么说（30 秒）**

> 我做过一次快照回滚实验，先拍快照再换系统，结果发现回滚按钮灰了。排查发现换系统不是格式化重装，而是换了一块全新的系统盘、旧盘被释放；快照是绑在盘上的，源盘没了就救不回当前实例。我的补救是在新盘上重拍快照、用删文件模拟灾难，同盘回滚成功。我还知道跨盘恢复的正解是把旧快照做成自定义镜像再用镜像重装。这个坑让我真正理解了快照绑盘不绑实例。

## C010　以为回滚后密码会变，试了几次才发现密码跟盘走

**环境**：同盘回滚快照后重新 ssh 登录

**现象**

按“回滚后要用拍快照时的旧密码”的提醒，反复用原来的密码登录，都失败；后来才反应过来——密码根本没变，一直是同一个。

**排查过程（含走错的路）**

我先怀疑是回滚把密码“时光倒流”了，于是来回试旧密码。想通之后的关键事实：这次是**同盘回滚**——盘从头到尾没换过，`/etc/shadow` 文件根本没动，所以前后是同一个密码。我把“换系统那次（盘换了、密码变了）”和“这次（盘没换、密码没变）”两组实验混在了一起，才产生了“密码会变”的错误预期。

**根因**

Linux 密码存在系统盘的 `/etc/shadow` 文件里（一串加密哈希），**密码跟盘走，不跟实例走、也不跟快照走**：

- 回滚 = 整块盘退回快照那一刻 = shadow 文件一起退回 = 能登的密码就是那一刻的密码
- 同盘回滚且密码从未修改 → 看起来“什么都没发生”

**修法 / 预防**

1. 判断密码问题先看“盘换没换”：换盘（换系统）→ 密码跟着新盘变；同盘回滚 → 密码跟当时一致
2. 两个延伸知识点：
   - 控制台“重置密码”本质是把新哈希写进 shadow，sshd 要**重启才重新读**，所以重置后必须重启实例
   - 跨盘的 shadow 文件不能直接搬：密码哈希带各盘自己的盐，搬过去也对不上
3. 方法论：**别把别人的结论当圣旨，拿事实验证结论**——这次验证失败反而逼出了底层模型

**面试怎么说（30 秒）**

> 我一开始以为快照回滚会把密码也“退回”旧值，结果用旧密码试了几次都登不上。后来想明白密码存在系统盘的 /etc/shadow 里，跟盘走不跟实例走：我这次是同盘回滚、密码从没改过，所以前后是同一个。换系统那次盘换了，密码才跟着变。顺带我也搞懂了为什么重置密码要重启生效——因为要改盘上的 shadow 让 sshd 重读。
